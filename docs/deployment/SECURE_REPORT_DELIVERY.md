# Secure report delivery

The repository includes a Meta WhatsApp Cloud API adapter, a server-only send ledger and signed status-webhook handling. It remains **disabled by default** (`503 not_configured`). No hosted migration, deployment, provider configuration or real message was performed during the remaining-work sweep.

## Implemented contract

- The app saves explicit recipient consent and queues the selected immutable 7/30-day report. Repeated queueing reuses the existing intent. It rejects changed contacts/scopes, revoked consent, wrong patients and mismatched report periods. Queuing is not a receipt.
- General cloud backup must be explicitly enabled for the owning account. Its existing outbox uploads the recipient, report and delivery intent. Local-only data never reaches the worker.
- `POST /functions/v1/report-delivery` accepts an owner access-token JWT plus exactly `{ "patient_id": "...", "delivery_id": "..." }`. `auth.getUser` establishes the owner; a caller cannot supply an owner, phone, message, snapshot, provider URL or receipt.
- Alternatively, the server scheduler supplies `x-report-worker-secret` and exactly `{}`. Each invocation handles at most three queued intents. Neither authentication route is available to the public without its credential. `verify_jwt=false` permits Meta callbacks; it does not disable the handler's authentication.
- Only the server's service-role client can call the claim/finish/pending RPCs. `report_send_jobs` has RLS and no public/anonymous/authenticated table access. The account lock used by normal sync serializes claims and consent updates. Recipient/member/report ownership and current report scopes are checked against persisted records. A changed recipient invalidates older queued consent.
- A unique owner/patient/recipient/period ledger entry prevents duplicate sends across delivery IDs and manual/7-day aliases. Client-supplied provider statuses are normalized; replayed queued records cannot overwrite server receipts. The original sync versions advance so existing pull clients receive the receipt.
- Messages contain a scoped factual text summary, not a PDF, photo, AI explanation or diagnosis. Cognitive, routine and memory counts require their corresponding selected scopes. No patient name, contact label, notes, coordinates or raw sessions enter the message. The approved template is English (`en`, `en_US` or `en_GB`); app languages and manual localized PDF sharing remain unchanged.
- Provider HTTP acceptance records `sent`, never `delivered`. Verified Meta HMAC callbacks advance sent/delivered/read/failed status; a delayed sent/failed event cannot undo delivered. Callback correlation uses a random per-attempt UUID, not patient data.
- Only explicit HTTP 429 rejections retry, at most three attempts, with persistent 2/4-minute backoff. Other definitive 4xx errors fail. HTTP 408/5xx, timeout, malformed success, failed acknowledgement or interrupted workers remain `sending`/`unknown` and **are not resent automatically**. Meta's send endpoint supplies no idempotency guarantee used here. A valid callback can settle an ambiguous send even if its initial response was lost. Operators must reconcile unresolved attempts with Meta; never blindly reset the ledger or create another recipient to force a resend.
- Authorization takes effect at the committed claim. Revoking consent prevents subsequent claims; it cannot recall a provider request already in flight. A denied queued intent is terminal and does not block later cron work.
- Audit state contains record IDs, attempts, fixed error codes, timestamps and provider receipt IDs. No message bodies, phone numbers, tokens or raw provider errors are logged. Treat the ledger as private linked data; retention is an operator decision, and deletion would remove duplicate protection.

Weekly/monthly selections remain saved preferences. This worker drains **explicitly queued snapshots**; it does not create recurring reports from those preferences. That existing product boundary is unchanged. The report screen confirms only “Share requested”; authoritative receipts are available in synced delivery records and the private ledger. Do not advertise automatic weekly/monthly report generation.

## External setup, in order

1. Confirm the intended Supabase project and inspect migration history. Review `20260929000000_secure_report_worker.sql` after the eight existing migrations. Run `supabase db push --linked --dry-run`, review the output and recovery plan, then apply the reviewed migration through the project's normal deployment process. No reset or production-data deletion is needed. The local test creates the hosted `service_role` role only in its disposable cluster; the migration does not create/alter hosted roles.
2. In Meta, provision the intended WhatsApp Business account and registered sender phone. Obtain a server access token with `whatsapp_business_messaging`, the **phone-number ID** (not its displayed phone number), the Meta app secret and a supported Graph API version for that app. Configure billing/provider eligibility and approved recipients as required by that account. These external facts were not verified here.
3. Approve an English text-only template with one **positional body text parameter** and no header/button parameters. Suggested exact body: `Smaran activity report: {{1}} This is not a diagnosis or medical advice.` The parameter is at most 950 characters; test the approved template's actual limits and category with Meta. Set its actual approved name and language; do not use a fabricated template ID or assume approval.
4. Copy [the server environment example](../../supabase/functions/report-delivery/.env.example) to an ignored secure local file or enter values directly in Supabase's secret manager. Set every named value; `WHATSAPP_GRAPH_VERSION` has the form `vNN.0`. Use independent random values of at least 32 characters for `WHATSAPP_VERIFY_TOKEN` and `REPORT_DELIVERY_WORKER_SECRET`. Keep `REPORT_DELIVERY_ENABLED=false` until acceptance is ready. The three `SUPABASE_*` runtime variables are server-provided. Never put service-role, Meta or worker secrets in `.env.example`, Expo/EAS public variables, SQL text, shell history or Git.
5. Deploy with `supabase functions deploy report-delivery --project-ref <intended-project-ref>`. The repository's `supabase/config.toml` specifies handler-side authentication. Disable any older delivery triggers/workers so there is only one sender.
6. Register `https://<project-ref>.supabase.co/functions/v1/report-delivery` as the Meta webhook callback. Set the matching verification token and subscribe the app/WABA to message status notifications. GET challenge verification uses the verification token; POST receipts require `X-Hub-Signature-256` over the exact raw body using the app secret. Callback metadata must match the configured sender phone-number ID. Keep platform request-header logging redacted.
7. With isolated accounts and approved test recipients, enable sending, consent and backup; generate and explicitly queue one report. Invoke the owner endpoint once or configure the scheduler below. Verify the real Meta message, signed receipt, recipient scopes, replay, rate-limit behavior and revocation. The local tests do not substitute for this acceptance. Disable sending again if acceptance fails.

## Optional queue scheduler

Use Supabase Cron/pg_net and Vault following the [official scheduling guide](https://supabase.com/docs/guides/functions/schedule-functions). Configure a job every two minutes that POSTs `{}` to the deployed endpoint with `Content-Type: application/json`, the project's public `apikey`, and `x-report-worker-secret`. Store the endpoint/public key/worker secret in Vault; fetch them in the scheduled SQL rather than pasting secret literals into the job. Set the HTTP timeout to cover a bounded three-job pass (up to roughly 100 seconds). Inspect the installed pg_net version's supported timeout setting before creating the job. Reuse one named job, not overlapping copies. The SQL account locks and ledger also guard concurrent invocations.

This external scheduler is not installed by a migration: enabling extensions, installing secrets and starting real sends requires the intended hosted account. Saving frequency preferences alone does not schedule messages.

## Validation and recovery

`node scripts/check-report-delivery.cjs` exercises the local SQLite queue and the actual TypeScript worker contract with synthetic HTTP responses. `node scripts/check-live-database-sync.cjs` applies all migrations to disposable PostgreSQL and runs `supabase/tests/report_delivery.sql`: RPC grants, ownership, duplicate claims/periods, receipt projection/replay, rate-limit exhaustion, uncertain outcomes and revoked scopes. Three Edge Function entry points also pass `deno check` in this sweep.

To stop new sends, set `REPORT_DELIVERY_ENABLED=false` and disable the cron job. Signed receipts can still reconcile existing attempts while sending is disabled. Preserve the additive migration and ledger during rollback; removing them would lose deduplication and receipt history. Reverting to the former disabled handler is safe only with all older sending triggers stopped. Reconcile ambiguous sends using provider evidence before considering any controlled recovery mutation; this repository provides no blind resend/reset command.

Contracts checked against [Meta's official message API collection](https://www.postman.com/meta/whatsapp-business-platform/folder/o48mro7/messages), [template messages](https://whatsapp.github.io/WhatsApp-Nodejs-SDK/api-reference/messages/template/), [status payloads](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/messages/status.md) and [signature verification](https://whatsapp.github.io/WhatsApp-Nodejs-SDK/api-reference/webhooks/start/). The SDK reference is archived; this implementation uses direct HTTP and the current status schema, not the archived SDK.
